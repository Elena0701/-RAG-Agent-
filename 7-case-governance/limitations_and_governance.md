## 1 系统定位、责任边界与免责基线

### 1.1 一句话定位

本系统对**目标企业已签署的商业合同**做**初审辅助**：找出指定条款、给出可回查的原文与位置、按**项目自设的审核政策**提示需要关注的事项与需人工确认的问题。

### 1.2 三类边界

| 边界类型     | 具体内容                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **能力边界** | 只处理 11 类任务（Q1–Q5 基本信息 + Q6–Q11 规则候选）；只处理可抽出文本的 PDF/TXT/JSON；只做合同内检索，**不接入法条或外部知识库**；规则只覆盖 6 条（`LAW-001` / `RENEWAL-001` / `NOTICE-001` / `INS-001` / `AUDIT-001` / `TERM-001`），且只比整数月/整数年与明示天数；不覆盖价款/金额一致性、关联交易、担保、知识产权归属细化等。**特别点名：1 号 `sample_manifest_draft.csv` 中的控制权变更（Change of Control）、转让限制（Anti-Assignment）、赔偿责任上限（Cap on Liability）、赔偿责任无上限（Uncapped Liability）四类，本轮既不在 11 类范围内、也无对应规则，属后续扩展维度，不作为本轮评价目标** |
| **依据边界** | 风险提示依据是**3 号 `risk_rules.yaml` 中项目自设的模拟内部政策**（允许法律清单、12 个月、60 天等），不是法律意见；规则`TRIGGERED` ≠ 违法；`NOT_TRIGGERED` ≠ 无风险；检索到的原文 ≠ 条款有效                                                                                                                                                                                                                                                                                      |
| **责任边界** | 系统输出为**待人工确认的初审事项**；`needs_manual_review=true` 只表示「已交付一项待处理事项」，**不表示有人审过**；最终判断由法务人员作出                                                                                                                                                                                                                                                                                                                               |

### 1.3 治理方案的总原则

1. **证据优先**：任何风险结论都必须能落到 `predicted_answers` 的合同原文，或 `review_results` 的 `rule_id` + 所用政策参数；两者都没有 → 输出「无法确认 / 依据不足」。
2. **规则约束**：能写成条件判断的审核要求，优先用程序执行，不交给模型自由裁量。
3. **不确定性升级**：检索不足、核验失败、规则 `UNCERTAIN` 时，**不强行输出确定结论**；状态未知一律取保守值。
4. **否定结论加严**：`No` 类结论必须过覆盖检查，且该检查在规则模块里是硬前置；「没检索到」不得写成「不存在」。
5. **过程可追溯**：合同来源、冻结哈希、块 ID、偏移、页码、检索历史、规则结果与政策参数、复核记录全部留存。
6. **人工保留决策权**：AI 输出是辅助材料，不是终局结论。

## 2 局限清单（按失效环节组织，L1–L10）

每条格式：**机制 / 可观测信号 / 量化依据 / 影响 / 治理 / 责任 / 验证状态**。

### L1 文档解析层

| 项     | 内容                                                                             |
| ----- | ------------------------------------------------------------------------------ |
| 机制    | 扫描件无 OCR；加密字体 PDF 抽出的字为乱码；无 `pypdf` 时仅标准库兜底                                    |
| 可观测信号 | `prepare.status`、`PDF_TEXT_EMPTY` / `PDF_TEXT_UNUSABLE` 原因码                    |
| 量化依据  | 空文本或低字符占比一律 `FAILED`，**不静默索引空文本**；本案例合同 `prepare` 约 7 ms（38,671 字符 / 80 块同级实测） |
| 影响    | 若整流为「空文本」，11 类会全判 `No`，把「读不出」说成「没有该条款」                                         |
| 治理    | 解析失败即停止自动审查，记录原因，提示人工处理原文件；报告中不得出现「无风险」字样                                      |
| 责任    | 5 号（模块）/ 4 号（流程分支）                                                             |
| 验证    | 已实现并有测试；CASE-001 未触发                                                           |

### L2 分块层

| 项     | 内容                                                                                                                                |
| ----- | --------------------------------------------------------------------------------------------------------------------------------- |
| 机制    | 按条款标题切块依赖正则；无编号长段落合同退回字符切块（800/120）                                                                                               |
| 可观测信号 | `chunk_strategy`（`clause` / `char_fallback`）                                                                                      |
| 量化依据  | 仅 **82%** 的 CUAD 合同命中 ≥3 个条款标题（中位数 18 个）；**CASE-001 命中 0 处，走字符切块兜底**。条款块相对字符块：span R@5 `0.713` vs `0.703`，精确@5 `0.744` vs `0.725` |
| 影响    | 条款可能跨块切断；检索排序被边界稀释；标题写法异常（全大写、居中、无编号）可能漏切                                                                                         |
| 治理    | 120 字符重叠兜底；`top_k` 提到 10（R@10 `0.815`）；运行时记录切块方式，供人工判断是否需要人工分段后重跑                                                                 |
| 责任    | 5 号                                                                                                                               |
| 验证    | 已复现（CASE-001），见 FC-02                                                                                                             |

### L3 检索层（本项目最实质的局限）

| 项     | 内容                                                                                                                                                                                       |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 机制    | 合同内 BM25；IDF/平均长度/词频只在当前合同内统计；query 依赖类别词表                                                                                                                                               |
| 可观测信号 | `query_source`（`explicit`/`template`/`none`）、`resolved_category`、块分数与排名                                                                                                                  |
| 量化依据  | 全量 510 份合同 / 6480 个 gold span：span R@1 `0.405`、R@3 `0.622`、R@5 `0.713`、精确@5 `0.744`、macro R@5 `0.754`、R@10 `0.815`。消融：只用问句 R@5 `0.338`；只用类别词表 `0.719`；**问句被改写后 `0.307`**（词表贡献约 +38 个百分点） |
| 影响    | ① 措辞与词表不一致时召回骤降；② 同义改写（`inspection` vs `audit`）与跨语言无解；③ 一份合同内的全部候选只来自 top-k，未召回区域天然存在                                                                                                    |
| 治理    | ① **强制显式传 `category`**（成本一行，收益最大）；② 补查时保持 `category` 不变、只扩写 query；③ `top_k` 动态提升至 10；④ 向量检索列为对照实验，**不默认上线**（理由：可复现性、零依赖、收益边界未验证）                                                         |
| 责任    | 5 号（模块）/ 4 号（调用契约）                                                                                                                                                                       |
| 验证    | 已复现，见 FC-07；向量对照未做                                                                                                                                                                       |

> **必须在论文里承认的一句话**：`0.713` 是在「显式传 `category` + 条款块」的最优配置下取得的；换成自然语言提问，同一模块只有 `0.307`。这不是调参问题，是词汇不匹配的方法边界。

### L4 抽取层（LLM）

| 项     | 内容                                                                                                                                                                                         |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 机制    | 模型只根据检索片段抽取 `category_answer` 与引文；偏移由程序定位                                                                                                                                                  |
| 可观测信号 | `processing_status`（`COMPLETED/INCOMPLETE/ERROR`）；答案要素完整性                                                                                                                                  |
| 量化依据  | 目前**没有独立人工标注**，不能写准确率；CASE-001 的抽取为契约示例，非运行结果                                                                                                                                              |
| 影响    | ① 要素混淆（把续约期读成通知期，见 FC-03）；② 就近取材、过度推断；③ 对否定与例外判断不稳；④ 提示词注入（FC-09）；⑤ 无依据时编造（FC-10）；⑥ **答案写法不规范化，规则层直接读不懂**（`5 years (automatic)`、`five (5) years` 都过不了 `RENEWAL-001` 的整串匹配，见 FC-12）         |
| 治理    | ① 提示词分「指令区 / 待审数据区」，数据区声明不构成指令；② 关键类别设**要素强制项**（如 Q8 必须「数字 + 时间单位 + 通知方向」）；③ 输出结构化字段，决策交程序；④ 依据白名单：结论只能引合同原文或规则 ID；⑤ **`category_answer` 按规则可消费的格式产出（纯数字 + 单位），原文细节放 `predicted_answers`** |
| 责任    | 4 号                                                                                                                                                                                        |
| 验证    | 待端到端运行                                                                                                                                                                                     |

### L5 证据核验层

| 项     | 内容                                                                                                             |
| ----- | -------------------------------------------------------------------------------------------------------------- |
| 机制    | 三道检查：位置（程序，不可覆盖）→ 语义（模型三态）→ 覆盖（程序，仅对 `No`）                                                                     |
| 可观测信号 | `position_valid`、`support_status`、`verification_status`、`coverage_status`、`model_calls`                        |
| 量化依据  | +5 字符偏移即 `FAILED` 且 `model_calls=0`；候选块位置自洽率 100%（块由原文切片生成）                                                    |
| 影响    | ① 语义核验**无独立人工标注**，`SUPPORTED` 目前靠模型自评或桩，**不可写成准确率**；② 锚定词覆盖检查是启发式，不是「条款不存在」的证明；③ 模型不可用时整批 `UNCERTAIN`，会造成升级率偏高 |
| 治理    | ① 位置核验失败不调用语义核验；② 未执行一律 `UNCERTAIN`，禁默认 `PASSED`；③ 报告显式标注「本次语义核验：已执行/未执行」；④ 锚定词表由 3 号按规则口径复核                   |
| 责任    | 5 号（模块）/ 3 号（锚定词）                                                                                              |
| 验证    | 已复现 FC-05、FC-06；语义准确率**尚无标注**                                                                                  |

### L6 规则层

| 项     | 内容                                                                                                                                                                                                                                                                                                        |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 机制    | `RuleTool.review()` 读九个字段，先判事实（`fact_status`），再执行已启用的政策，输出 `review_results`（四态）与 `requires_manual_review`。规则程序是**确定性代码**：正则解析答案、比较阈值、不做推断，也不调用模型                                                                                                                                                          |
| 可观测信号 | `fact_status`、`rule_execution_status`、`review_results[].status` / `risk_level` / `missing_fields`、`requires_manual_review`                                                                                                                                                                                |
| 量化依据  | 已交付 6 条规则（`LAW-001` / `RENEWAL-001` / `NOTICE-001` / `INS-001` / `AUDIT-001` / `TERM-001`），`enabled` 全为 true；政策值：允许法律 `["California","New York"]`、续约上限 `12` 个月、通知阈值 `60` 天（`AS_WRITTEN_DAYS`）。3 号本地 44 项测试通过，**测试文件未上传**；**未与 4 号、5 号端到端联调**                                                              |
| 影响    | ① **答案写法决定能否执行**：`5 years` → TRIGGERED；`5 years (automatic)`、`five (5) years`、`twelve months` → 全部 UNCERTAIN（本机实测，见 FC-12）；② 布尔类别只认精确的 `Yes` / `No`，小写 `no` 直接进 `missing_fields`；③ 只比整数月/整数年，天数不换算，复杂窗口一律不判；④ 阈值与清单是演示政策，换参数结论就变，且**程序不实时监控配置文件变化**；⑤ 类别缺失导致能力外场景（FC-08 金额矛盾）                             |
| 治理    | ① 无法判断一律 `UNCERTAIN` + `missing_fields`，**不硬判未触发**；② 区分「事实确认但政策无法判断」（`CONFIRMED` + `UNCERTAIN`）与「事实无法确认」（`UNCERTAIN`），不许混为一谈；③ `review_results=[]` 只表示未配置或未启用，**不等于无风险**；④ 结果必须与所用政策参数一起保存（3 号明确要求）；⑤ 配置类故障单独记 `RULE_CONFIG_INVALID`，不冒充「未触发」；⑥ **抽取侧必须输出规范化的 `category_answer`**，否则规则形同虚设（本条是 7 号在实测后补的） |
| 责任    | 3 号（规则与配置）/ 4 号（答案规范化）                                                                                                                                                                                                                                                                                    |
| 验证    | ✅ 模块级已实跑（六规则、边界、事实描述、缺项）；⛔ 端到端未联调                                                                                                                                                                                                                                                                         |


> **这一层最容易误读的三件事**（3 号文档已写明）：
>
> 1. `NOT_TRIGGERED` ≠ 无风险，只表示「本项政策要求已满足」；
> 2. `NOT_APPLICABLE`（政策不要求该检查）≠ 未启用（`enabled=false`）≠ `NOT_TRIGGERED`（执行了但没触发）；
> 3. `risk_level` 只在确定触发时才有值，`null` 不代表低风险。

### L7 编排与决策层

| 项     | 内容                                                                                                                   |
| ----- | -------------------------------------------------------------------------------------------------------------------- |
| 机制    | `decide_next_action()` → `ACCEPT / RETRY / ESCALATE`；`max_retries=2`（首次 + 最多两次补查），每任务独立计数                            |

| 验证    | 未运行                                                                                                                  |

## 3 风险矩阵与优先级

**可能性**（在本项目条件下发生的概率）× **影响**（对尽调结论的伤害）。

| 风险                  | 对应              | 可能性         | 影响                | 优先级    | 首要动作                                            |
| ------------------- | --------------- | ----------- | ----------------- | ------ | ----------------------------------------------- |
| `No` 结论覆盖不足即判「不存在」  | L5 / FC-04      | 高           | **极高**（否定性结论被当事实） | **P0** | 覆盖检查强制前置，`INSUFFICIENT` 不得输出结论                  |
| 语义核验未执行被当通过         | L5 / FC-06      | 中           | 高（报告看起来完整）        | **P0** | 默认 `UNCERTAIN`；加回归测试断言                          |
| 要素混淆（续约期 ↔ 通知期）     | L4 / FC-03      | 高           | 高（有据的错误）          | **P0** | 要素强制项 + 语义核验加要素一致性                              |
| 规则核验未接入即被表述为已运行     | L6              | 中（已交付，但未联调） | 高（文档失真）           | **P0** | 状态标记纪律：模块级实跑要写「模块级」，端到端没跑就不能写端到端                |
| **规则触发被「重试」洗成无法确认** | L6 / L7 / FC-12 | **高**       | **高（风险提示消失）**     | **P0** | `TRIGGERED` 不进 RETRY；`category_answer` 规范化后再入规则 |
| **答案格式与规则正则不匹配**    | L4 / L6 / FC-12 | 高           | 中高（结论从触发退化）       | **P1** | 抽取输出契约 + 规则侧 `missing_fields` 显式提示              |
| 措辞失配导致召回骤降          | L3 / FC-07      | 高           | 中高                | **P1** | 强制显式传 `category`；`query_source` 入日志             |
| 扫描件/乱码 PDF          | L1 / FC-01      | 中           | 高                 | **P1** | 失败即停，不静默                                        |
| 条款跨块 / 标题未命中        | L2 / FC-02      | 中高          | 中                 | **P1** | 重叠 + `top_k=10`，记录 `chunk_strategy`             |
| 位置偏移 / 引用不可回查       | L5 / FC-05      | 中           | 中高                | **P1** | 偏移由程序定位；哈希随结果传递                                 |
| 提示词注入               | L4 / FC-09      | 低中          | 中高                | **P1** | 指令区/数据区隔离；决策程序化                                 |
| 无依据时编造法条            | L4 / FC-10      | 中           | 中高                | **P1** | 依据白名单                                           |
| 能力外场景被当作系统缺陷        | L6 / FC-08      | 高           | 中（影响指标解释）         | **P2** | 改定位并单列「能力边界测试」                                  |
| 单实例非并发              | L7              | 低（当前）       | 低                 | **P3** | 标注边界，上线前改造                                      |
| 数据外泄                | L9              | 低           | **极高**            | **P1** | §8 措施表                                          |

> 读法：P0 四项的共同点是「**会让报告看起来比实际更可信**」。这类失效比「明显报错」危险得多，所以优先处理。

## 4 治理机制的五个闸门

```
闸门1 输入准入 → 闸门2 检索覆盖 → 闸门3 证据三道核验 → 闸门4 规则边界 → 闸门5 决策升级
   (L1/L2)          (L3)              (L5)                (L6)            (L7)
```

| 闸门     | 拦什么                | 判定条件                                                                             | 拦截后动作                          | 责任      |
| ------ | ------------------ | -------------------------------------------------------------------------------- | ------------------------------ | ------- |
| ① 输入准入 | 抽不出字、乱码、切块异常       | `prepare.status != SUCCESS`；`chunk_strategy=char_fallback` 记警告                   | 停止自动审查 / 提示人工分段                | 5 号     |
| ② 检索覆盖 | 检索不到、`No` 覆盖不足     | 无候选块；`coverage_status=INSUFFICIENT`                                              | 扩词 + 提 `top_k` 补查（≤2 次）        | 5 / 4 号 |
| ③ 证据核验 | 位置错、语义不支持、核验未执行    | `position_valid=false`；`UNSUPPORTED`；`UNCERTAIN`                                 | 补查或升级；`FAILED` 不进入语义核验         | 5 号     |
| ④ 规则边界 | 事实无法确认、政策无法判断、配置故障 | `fact_status=UNCERTAIN`；`status=UNCERTAIN`；`RULE_CONFIG_INVALID`                 | 缺信息先补查/补配置；语义复杂直接升级；**触发不进重试** | 3 / 4 号 |
| ⑤ 决策升级 | 重试预算耗尽 / 规则要求复核    | `retries = max_retries = 2`；`status=TRIGGERED` + `manual_review_on_trigger=true` | `ESCALATE`，生成 11 字段复核包         | 4 号     |

**闸门设计的一条硬规则：任何闸门都不得「默认放行」。** 状态未知 → `UNCERTAIN` / `ESCALATE`，而不是 `PASSED` / `NOT_TRIGGERED` / `ACCEPT`。这一条在 3 号的实现里已经做到了：`enabled` 类型不对、`risk_level` 非法、阈值缺失，一律返回 `UNCERTAIN`，不会退化成「未触发」。

## 5 人工复核机制（与 4 号实现对齐）

### 5.1 触发条件

| #  | 触发条件          | 对应状态                                                 | 原因码                     |
| -- | ------------- | ---------------------------------------------------- | ----------------------- |
| 1  | 合同解析失败        | `prepare.status=FAILED`                              | `PREP_FAILED`           |
| 2  | 抽取未完成         | `processing_status ∈ {INCOMPLETE, ERROR}`            | `EXTRACT_INCOMPLETE`    |
| 3  | 引用位置对不上       | `position_valid=false`                               | `POSITION_INVALID`      |
| 4  | 原文存在但不支持结论    | `support_status=UNSUPPORTED`                         | `SUPPORT_UNSUPPORTED`   |
| 5  | 语义核验未执行或结论不确定 | `verification_status=UNCERTAIN`                      | `SUPPORT_UNCERTAIN`     |
| 6  | `No` 结论覆盖不足   | `coverage_status=INSUFFICIENT`                       | `COVERAGE_INSUFFICIENT` |
| 7  | 规则模块判定事实无法确认  | `fact_status=UNCERTAIN`（`missing_fields` 非空）         | `FACT_UNCERTAIN`        |
| 8  | 规则已触发且政策要求复核  | `status=TRIGGERED` + `manual_review_on_trigger=true` | `RULE_TRIGGERED_REVIEW` |
| 9  | 已启用规则无法判断     | `status=UNCERTAIN`（缺参数或答案不可比较）                       | `RULE_UNCERTAIN`        |
| 10 | 政策配置缺失或非法     | `rules.<id>.enabled` / `risk_level` / 阈值类型错误         | `RULE_CONFIG_INVALID`   |
| 11 | 重试预算耗尽        | `retries=2`                                          | `RETRY_EXHAUSTED`       |

### 5.2 复核处理结果

| 状态                  | 判定标准                                 |
| ------------------- | ------------------------------------ |
| `ACCEPT`            | 结论、引文、规则触发判断均与人工阅读原文一致               |
| `MODIFY`            | 方向对，风险描述/等级/建议需改（必须写「改前 → 改后」）       |
| `REJECT`            | 条款识别错误、引文不支持结论、或规则不应触发（必须归为 FN 或 FP） |
| `INSUFFICIENT_INFO` | 原文或政策不足（写明缺原文 / 缺政策参数 / 缺适用法域）       |

### 5.3 复核记录与回流

必存字段见 `case_01.md` §6.1（11 项，含 `fact_status`、`clause_description`、`missing_fields` 与所用政策参数）。回流路径见 `case_01.md` §6.3：`REJECT`-FN → 补词表/规则；`REJECT`-FP → 收紧提示词或规则；`INSUFFICIENT_INFO`（政策）→ 补配置；`INSUFFICIENT_INFO`（答案格式）→ 改抽取输出契约（FC-12）；仍不足 → 记残余风险（§9）。

## 9 残余风险、不适用范围与免责声明

### 9.1 残余风险（治理后仍然存在，需明示）

1. 语义核验无独立人工标注，`SUPPORTED` 只能说明「模型自认为支持」，不能说明「法律上成立」。
2. 覆盖检查基于锚定词，**锚定词表本身是人工初稿**，可能漏掉同义表述。
3. 规则阈值是项目自设，换一套政策，风险结论会变。
4. 补查上限为 2 次，复杂合同可能需要更多轮，系统会提前升级。
5. 单实例顺序执行，未做并发与大批量压测。
6. 未接入外部法律知识库，凡涉及法条效力的判断均未评估。

### 9.2 不适用范围

- 中文合同、非美国法域合同（当前规则与词表均面向英文 CUAD 合同）；
- 扫描件、图片型 PDF、加密字体 PDF；
- 需判断合同效力、违约责任成立与否、担保有效性等法律定性问题；
- 关联交易公允性、税务、反垄断等需专门尽调的事项；
- 条款类型超出 Q1–Q11 的审查需求。

### 9.3 报告免责声明模板

> 本报告由「基于 RAG 与规则核验的商业合同初审 Agent」自动生成，用于**辅助**识别合同条款、定位原文证据并按项目自设的审核政策提示关注事项。
>
> 1. 本报告**不构成法律意见**，不能替代执业律师或法务人员对具体合同的审查与判断。
> 2. 报告中的「风险等级」依据项目预设的模拟内部政策得出，**不代表条款违法、无效或不可签署**。
> 3. 标注「未评估 / 无适用规则」的类别表示当前规则未覆盖，**不代表该类别没有风险**。
> 4. 标注「需人工复核」表示系统已将该事项转交人工，**不代表已完成人工审查**。
> 5. 系统仅处理可抽出文本的英文商业合同，且仅覆盖 11 类审查任务；超出范围的事项未作判断。
> 6. 报告结论仅适用于所审文本（冻结哈希：`______`）与所用规则版本（`______`）；文本或规则变更后结论可能失效。
