# 选题与研究背景

## 一、选题

**基于 RAG 与规则核验的商业合同初审 Agent——面向投资并购尽职调查的辅助审查**

本项目选择投资并购尽职调查中的商业合同初审作为应用场景，站在潜在投资方或收购方的视角，辅助审查目标企业已经签署的商业合同。具体规则判断还需明确目标企业在各份合同中的身份，例如客户、服务提供方、许可方或被许可方；不同角色的权利义务不能混用。主体或立场无法确认时，应列为待确认事项。

这里的审查对象包括服务、供货、许可、合作等合同。投资并购是使用系统的业务场景，合同本身则是目标企业日常经营中形成的商业合同。CUAD 的官方说明也将并购、投资等企业交易列为其相关使用场景，因此这一选题与数据集的设计用途相符。<sup>[1]</sup>

项目拟从 CUAD 中选取有限样本及若干目标条款，结合 RAG 检索、预设审核规则和证据校验，形成包含条款位置、关键约定、提示理由与待人工确认事项的初审结果。

选择这一题目，主要有三个理由：

1. **业务需求具体。** 企业现有合同中的终止权、转让限制和责任安排，都是尽职调查中可以明确提出、逐项核查的问题。
2. **数据能够支持验证。** CUAD 提供合同原文和条款标注，可以检查系统是否找对了条款、引用了正确证据。
3. **研究范围可控。** 项目聚焦有限类别的辅助初审，研究如何将检索、规则和证据组织成可复核的流程。

## 二、研究背景与研究问题

投资并购尽职调查需要了解目标企业的经营状况及其承担的义务，商业合同审查是其中的一项基础工作。目标企业已经签署的服务、供货、许可和合作等合同，记录了业务开展所涉及的权利、履约条件与责任安排，是商业合同审查的重要依据。合同中的终止权、转让限制、控制权变更及赔偿责任等约定，可能成为交易前需要进一步核查的事项。CUAD 将这些企业交易相关的审查需求作为数据集的重要应用背景，为研究提供了公开的商业合同及专家标注。<sup>[1]</sup>

这一工作的首要困难，是从大量合同文本中准确找出值得审查的内容。重要约定可能分散在不同章节，适用条件、例外和补充规定也可能出现在其他位置。审查人员不仅需要确认是否存在某类条款，还需要弄清条款约束谁、在什么条件下生效，并保留可供核查的原文依据。CUAD 原始论文将这一过程概括为从长合同中识别关键条款，并指出，进一步的风险判断还取决于企业的业务模式、风险偏好和具体背景。<sup>[2]</sup>

因此，本项目需要解决两个相互衔接的问题：一是“相关条款在哪里、具体说了什么”，二是“依据当前审核要求，哪些内容需要提示或进一步确认”。单纯提供一段合同摘要，难以完整呈现条款位置、规则适用条件及判断依据；仅找到关键词，也不足以确认相关约定是否满足审核条件。系统需要将信息定位、条件核查和结果说明连接起来，使审查人员能够逐项检查输出。

RAG，即检索增强生成，为解决信息定位与证据支持问题提供了方法。本项目拟先从指定合同中检索相关片段，再由模型结合这些片段提取关键信息、形成说明。采用这一方法的目的，是让输出围绕实际合同展开，并能够回到原文核查。同时，检索可能遗漏内容，检索到的片段也可能缺少必要上下文，因此还需要检查证据是否完整、是否支持相应结论。

在此基础上，引入 Agent，是为了组织多步骤的审查流程。合同初审涉及检索、信息提取、规则调用、证据核对及结果整理等连续操作。例如，识别出合同终止条款后，还需要提取享有终止权的主体、触发条件和通知期限，再依据预设审核政策判断是否需要提示。Agent 拟负责协调这些步骤，并在证据不足时进行有限补充检索，将仍无法确认的事项标记为待人工复核。

据此，本研究拟构建结合 RAG、规则核验与证据校验的商业合同初审 Agent，重点解决条款定位费时、审核条件难以逐项核查，以及输出理由不易追溯的问题。项目以 CUAD 的条款标注检验识别和证据定位情况，另行明确风险提示所依据的审核规则。研究价值在于探索一套能够适应具体审核要求、便于人工检查的辅助审查流程，其实际效果由后续实验验证。

因此我们提出研究问题：如何构建结合 RAG 与规则核验的商业合同初审 Agent，实现目标条款识别、依据预设审核政策生成风险提示，并提供可追溯的原文证据与人工复核信息？

## 三、数据来源与数据介绍

### 3.1 数据来源

本研究采用 Contract Understanding Atticus Dataset（CUAD）v1。该数据集由非营利组织 The Atticus Project 组织建设，合同来自美国证券交易委员会（SEC）的 EDGAR 公开披露系统。数据共包含 510 条英文商业合同记录，按合同名称归为 25 类合同类型，例如服务、供货、咨询、许可、分销和合作协议；另外，数据集为每份合同设置相同的 41 类条款审查问题，例如合同期限、转让限制、终止权及责任限制。因此，“25 类”说的是合同类型，“41 类”说的是要检查的条款或信息类别。标注人员经过培训后开展人工标注，并由经验丰富的律师参与审阅与质量检查。该数据集旨在为商业合同条款识别提供专业标注，支持合同审查工具的开发与评价。<sup>[2][3]</sup>

投资并购尽职调查中，审查人员通常需要查看目标企业在日常经营中签订的合同，例如服务、供货、许可和合作合同。本项目使用 CUAD 中这类商业合同，研究如何辅助审查；它们用于模拟尽职调查中会遇到的合同，不代表某一家目标企业的完整合同档案。

本地下载记录显示，项目于 2026 年 11 月 2 日从官方 GitHub 仓库的 `data.zip` 获取 JSON 数据，对应仓库版本为 `67faa0e6023b04fcaae6cc09497ab00e5d63a2a2`；同时查阅了官方 Hugging Face 发布目录及 README。CUAD 标注采用 CC BY 4.0 许可，使用时应注明来源；官方对底层公开合同的许可状态另有说明。<sup>[3][4]</sup>

### 3.2 数据规模与文件形式

官方完整发布资料包括合同 PDF、合同 TXT、条款汇总表、按类别整理的 Excel 表和 SQuAD 风格 JSON。本项目目前主要使用本地 JSON；本地 `data.zip` 实际仅包含 `CUADv1.json`、`train_separate_questions.json` 和 `test.json` 三个 JSON 文件，没有 PDF、TXT 或 Excel 文件。<sup>[3]</sup>

对本地 `CUAD/data/CUADv1.json` 全量读取后的统计如下：

| 统计项目 | 本地核对结果 | 含义 |
|---|---:|---|
| 合同条目 | 510 | 合同记录数 |
| 问题类别 | 41 | 每份合同均设置相同的 41 类审查问题 |
| 合同—问题条目 | 20,910 | 510 × 41，不是合同数量 |
| 有答案的条目 | 6,702 | 至少有一个对应的原文标注片段 |
| 无答案的条目 | 14,208 | 对应问题的答案列表为空 |
| 答案片段 | 13,823 | 同一问题可能对应多个片段 |

上述精确数字来自本地 JSON 统计。本研究统一按 CUADv1.json 中的 510 份合同记录统计，不按正文内容合并或扣减记录。“答案片段数”与“有答案的条目数”口径不同，也不直接等同于论文中的条款计数。本地配套训练文件与测试文件分别包含 408 条和 102 条合同记录，按合同标题检查，两者无交集。训练文件有 22,450 个问答条目，测试文件有 4,182 个；训练文件与完整 JSON 的问答组织不同，不能将训练问答数写成 408 × 41，也不能与完整 JSON 的条目数直接相加。

### 3.3 问题内容与标注结构

41 类问题涉及合同名称、当事方、日期、续约、适用法律、竞争限制、终止权、控制权变更、合同转让、知识产权和赔偿责任等。它们是审查类别，不是 41 种风险等级。官方汇总标注中，33 类具有“是／否”的派生答案，另外 8 类涉及名称、日期或期间等信息；本地问答 JSON 主要保存对应的原文片段及其位置。<sup>[3]</sup>

JSON 的层级为 `data → 合同记录 → paragraphs → context / qas → 问题记录 → answers`。下表中的字段分属这些不同层级，并非全部并列。

| 字段 | 含义 |
|---|---|
| `title` | 合同名称或文件标识 |
| `context` | 用于查找答案的合同文本 |
| `question` | 要求识别的类别及其英文说明 |
| `answers` | 原文答案片段列表，可以为空或包含多个片段 |
| `text` | 一个答案片段的原文 |
| `answer_start` | 片段在原文中的起始字符位置，从 0 开始 |
| `is_impossible` | 是否没有该问题的标注答案 |

例如，本地 SIBANNAC 战略联盟协议的“合同转让限制”问题标注了如下原文：

> This Agreement shall not be assignable by either party without the prior written consent of the other party.

其含义是：任何一方未经另一方事先书面同意，不得转让本协议。其 `answer_start = 7605`，表示这段答案在合同原文中的起始位置。由于程序将第一个字符编号为 0，因此编号 7605 对应我们通常所说的第 7606 个字符，即跳过前 7605 个字符后，便到达答案的开头；字母、空格、标点和换行都计入字符数。程序结合这一位置和答案文本的长度，就能从原文中取出对应片段，供审查人员核对引用依据。该位置以数据集保存的原文为准，重新排版或翻译后不能直接沿用。同一合同的“控制权变更”问题没有标注答案，不能仅凭合同存在转让限制，就推断它也约定了控制权变更限制。

### 3.4 有答案、无答案及使用边界

“有答案”表示该问题存在人工标注的相关文本；“无答案”表示该问题没有对应的标注片段。有答案样本可用于检查条款识别和证据定位是否正确，无答案样本可用于检查系统是否输出了标注中不存在的对应条款；若系统给出了人工标注答案之外的其他合同片段，即“额外片段”，还需回到原文核查其是否真实存在、是否与当前问题相关。例如，人工答案标出了合同转让的限制条件，系统还找到了另一处关于转让例外的规定，这可能是有用的补充。因此，不能仅凭片段未被人工标注就认定它是编造的，也不能未经核查就认定它正确。两类样本都有评估价值，不能将其分别等同于“有风险”和“无风险”。

评估时，我们先把合同全文和需要检查的条款类别交给系统，让系统自行查找相关内容。例如，要求系统找出“合同转让限制”，系统需要从全文中找出对应条款，并指出原文位置。系统完成后，再将其结果与 CUAD 的人工标注进行比较，检查是否遗漏条款、是否找错内容，以及引用位置是否准确。

人工标注相当于核对结果时使用的参考答案，应与系统输入分开保存，不能在系统查找前直接提供给它。这里限制的是提前提供“人工已经选好的答案及其位置”，并不是禁止系统阅读合同原文中的相关条款。如果系统找到了人工标注之外的内容，还需回到原文核查。这样的比较主要检验系统能否找到条款；至于条款是否需要提示风险，还要依据小组另行制定的审核规则判断。

CUAD 的人工标注主要支持条款识别和信息提取，不能直接充当完整商业风险判断的标准答案。它没有直接提供本项目所需的统一审查立场、审核政策及高／中／低风险等级。风险提示需要另外明确规则，并设置相应的人工参考或规则核对标准。部分公开合同存在遮盖内容和文本转换问题；EDGAR 披露样本和 41 类标注不代表全部商业合同，也不能直接推及中文合同或不同国家法律下的审查结论。合同原文用于识别其记载内容，并非现行法律知识库；如后续规则涉及法律效力，应另行核对适用法域、规则来源与生效时间。研究结论应限定在所选样本和任务范围内。<sup>[2][3]</sup>
