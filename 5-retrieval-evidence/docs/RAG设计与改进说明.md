# 第 5 部分：RAG 设计、问题诊断与 v1.4 改进

日期：2026-11-05。范围固定为 11 类。对外 `prepare/retrieve/verify` 的参数与原有返回字段保持兼容；内部新增候选排序模块。以下结果是本机真实固定版本 Embedding 模型的离线运行结果，未调用收费 DeepSeek API。

## 1. 小组各自负责什么

4 号 Agent 确定类别和问题，调用检索，从返回原文中抽取答案与引用，再调用核验。第 5 部分负责提供证据、检查引用的位置和语义支持关系。3 号读取核验结果并执行风险规则。检索返回的候选不等于识别答案，核验通过也不等于法律审查结论。

调用顺序：`prepare → retrieve → Agent 抽取 → verify → Agent 调用规则模块`。

## 2. 解析与冻结全文：统一证据的坐标

代码：`rag_core/pdf_ingest.py`。

PDF 用 pypdf 按页提取；TXT、Markdown、单合同 JSON 读取文本。处理多余空白后冻结全文；页码区间在规范化后计算。每条引用位置都针对这份冻结文本，不针对 PDF 文件字节或未经规范化的原文。

作用：让所有人使用同一把尺子。`context[start:end] == quote` 可直接由程序验证，模型不能把改写后的句子伪装成逐字引用。

本次增加：某页提取不到文字时记录原始页号的警告。可能是空白页，也可能是扫描图片；系统不能假定后者不存在。存在解析警告时，否定答案的覆盖检查保守返回不足。

限制：没有实现 OCR 和表格版式重建。页码表示块起点所在页，不能理解为块只位于这一页。

## 3. 分块：把长合同变成可检索的原文片段

代码：`rag_core/index.py`。

优先识别 ARTICLE、Section、编号等标题，再将过长条款切成默认最多 800 字符的片段，内部切分重叠 120 字符。标题不足时退回字符分块。每块保存 start/end，重叠可以降低证据恰好落在切分边界上的损失。

句子检索是可选实验：用短句搜，返回它所属的原始父块，帮助保留上下文。默认仍使用条款块。长句已保证检索单元不超过上限。

为什么本次没有盲目扩大块：在开发与回放数据中，若事后知道 gold 位置，当前分块都能用至多五个相关块覆盖标注的 80%。这是“理想选块上限”的诊断，不是系统实际召回率，也不证明语义上下文完整；但说明先改排序比直接更换所有分块更有依据。

超出 max_chunks 时拒绝索引，防止只审了前半份合同却声称审过全文。

## 4. Embedding：按意思寻找相关片段

代码：`rag_core/embedding.py`。

使用本地 `sentence-transformers/multi-qa-MiniLM-L6-cos-v1` 固定 revision。合同块变成归一化向量；问题也变成向量；用余弦相似度比较。当前合同块数量不大，直接精确矩阵检索，未引入额外向量数据库或近似索引。

作用：补充关键词不一致但意思相近的表达。DeepSeek API 不负责这里的向量编码。

发现并修复的错误：旧纯向量模式关闭语义扩展后，仍会收到 BM25 关键词串。现在纯向量消融确实使用原始问句；混合模式给向量端追加自然语言类别说明；关键词串只交给 BM25。

查询向量缓存限制为 512 条，避免 Agent 长期运行导致无界增长。文档向量按合同、模型版本、配置与实际分块内容校验缓存，防止旧分块和新向量错配。

## 5. BM25：按明确词语寻找相关片段

代码：`rag_core/index.py`、`rag_core/categories.json`。

已确定类别有专属词表，例如保险包含 insurance、policy、coverage 等。把词表和 Agent 问句一起用于 BM25，根据词在合同中的分布和块长度排序。关键词扩展只基于明确类别或固定模板问句，不承担自由意图识别。

作用：针对名称、日期、法律术语等明确字面表达提供稳定候选。当前任务上 BM25 比通用向量模型强，保留它是实验支持的决定。

## 6. 候选融合与结构补充：决定哪些证据进入前五名

代码：`rag_core/ranking.py`，由 `HybridIndex` 调用。

对于默认 top_k=5，先各取向量与 BM25 的前 20 个候选。按排名计算加权 RRF 分数，避免直接相加量纲不同的余弦分数和 BM25 分数。

旧方案几乎锁定 BM25 前五名，仅容许一个高相似度向量候选替换。普通 RRF 放开竞争后在开发数据反而退化。最终采用结构补充的保守混合：

1. 保留有较强表现的 BM25 候选，以及达到原有 0.75 门槛的新增语义候选。
2. 名称任务加入首块；当事方在前 2400 字符内找 between/among，签署日期找 dated/as of 等，生效日期找 effective/commence。最多优先加入两块；其他七类不强制加入开头。
3. 所有结构候选仍是已索引的真实原文块，不编造摘要、答案或位置。
4. 去掉重复 ID，以及重叠长度超过较短块 85% 的候选，把有限的五个位置留给不同证据。
5. 从剩余融合候选补足，至多返回 top_k 个块。

这些是候选选择规则，不是风险规则。开头出现的日期未必是签署日期，因此仍要由 Agent 抽取和 verify 核验。

`score` 仍记录融合分数，结构优先会改变最终次序。消费者应以 `rank` 和列表顺序为准；不得再按 score 自行排序。`retrieval_sources` 可以包含 structure，便于解释证据来源。

已有 CrossEncoder 重排保留为可选实验，默认关闭；本次未下载更大模型，也没有把提高效果归因于更强模型。

## 7. 位置核验：检查引用是不是原文

代码：`tools/rag_tool.py` 的 verify。

先检查引用格式、偏移类型、是否越界，再逐字比对。错位返回 FAILED，语义模型不参与覆写程序结果。通过后才进入语义核验。

同一个 document_id 重新准备失败时，现在清除旧文档状态，防止下一次查询意外搜到上一份合同。成功重新准备也清空检索历史。

## 8. 语义核验：原文是否支持抽取答案

代码：`rag_core/semantic_review.py`、`rag_core/deepseek_client.py`。

将类别判断标准、答案、引用和冻结全文交给 DeepSeek。模型检查主体、条件、否定词、例外、日期与单位；返回每条引用和整体答案的支持状态。程序严格验证返回格式与引用索引，调用失败或输出不合法返回 UNCERTAIN。

本次增加全文长度预算：超过 120000 字符返回 SEMANTIC_CONTEXT_TOO_LARGE，未调用模型，不偷偷裁掉合同后半部分。字符预算不是精确 token 上限；后续可改成分段审阅，但必须处理跨段例外和定义。

当前真实 DeepSeek 服务未在本次重调，语义边界通过注入可控模型响应测试；本次真实模型测试针对本地 Embedding。

## 9. No 的覆盖检查：防止漏检被当成不存在

代码：`rag_core/coverage.py`。

全文找该类别锚定词，检查这些位置是否被本轮历史涉及的已返回片段覆盖。仅接受工具实际返回过的 chunk ID，拒绝调用方随便列出一个未返回的块来宣称检查过；这仍依赖 Agent 如实保存每轮历史，不是加密审计日志。

本次修复一个重要逻辑错误：关键词全部覆盖，只证明检索检查过相关位置，不能证明答案 No 正确。即使明文写着保险义务，旧代码也可能因覆盖充分而放行空引用 No。现在所有空引用答案都 UNCERTAIN；有支持引用的 No 还需通过语义核验和覆盖检查。

零锚点、解析有警告、未覆盖锚点都不能确认不存在。系统会因此保留更多待复核项，这是为了避免错误的确定性否定。

## 10. 评测：区分候选找不到与排序没选中

脚本：`evaluation/diagnose_ranking.py` 与 `evaluation/evaluate_rag_tool.py`。

本次固定抽取官方 train 标题 SHA256 取模为 0 的约 20% 合同，共 74 份。比较四个预设方案，按开发集 Recall@5、宏平均 Recall@5、Recall@1 依次选优。选出的方案再在官方 test 的 102 份上回放；回放不重新选方案。

由于前期已查看过全部 510 份合同，这不是未见测试集。论文应称“固定开发子集选择及官方测试划分上的回顾性评估”，若要证明泛化还需新合同。

统计修复：同起点不同长度标注不再误去重；精确命中要求覆盖对应位置；失败合同留在分母；微平均从整数命中数计算，避免分类别四舍五入传播。

| 方法 | 开发集 Recall@5 | 回放 Recall@5 | 回放 Recall@1 |
| --- | ---: | ---: | ---: |
| BM25 | 69.28% | 71.77% | 41.78% |
| 旧保守混合，重算 | 69.28% | 72.38% | 41.78% |
| 普通 RRF | 54.94% | 未作为最终方案回放 | — |
| 结构补充 + RRF | 75.39% | 未作为最终方案回放 | — |
| 当前结构补充 + 保守混合 | 78.59% | 79.80% | 57.84% |

开发集 1032 条标注，双路候选并集覆盖 938 条，其中 223 条被旧前五名筛选漏掉。向量前二十名能补回 BM25 前二十名漏掉的 31 条。解释：向量确有互补，但幅度有限；排序和合同结构利用是本轮更大的改进来源。

| 类别 | 旧混合 Recall@5 | 当前 Recall@5 |
| --- | ---: | ---: |
| 合同名称 | 43.14% | 78.43% |
| 当事方 | 74.77% | 81.58% |
| 签署日期 | 76.34% | 86.02% |
| 生效日期 | 52.38% | 70.24% |

其余七类本次回放指标未变，审计权仍只有 58.10%。不能把这次提升描述为所有法律条款理解能力增强。Recall 是证据召回率，不是答案准确率或风险判断准确率。

默认公开三个方法的参数签名、引用结构、核验状态枚举均有兼容性测试。评测逐条断言实际 retrieve 返回的区间和被评方案一致，防止只在实验脚本里出现提升。

## 11. 仍值得继续做的事

- 审计权的上下文与同义表达是目前明确短板，应单独整理漏检案例；通用模型换法律模型是否有效需要新的开发实验。
- 当前 gold 是人工标注，不保证穷尽所有合理证据；指标低不一定等于合同没有其他有效表述。
- 本次覆盖 CUAD 官方划分中的多种合同，尚未按小组选定的服务/维护等合同类型单独报告结果。
- 扫描 PDF、复杂表格与长合同分段语义核验仍待实现。
- 本工具是有状态的本地实例，默认最多驻留 8 份合同；多用户并发服务需要单独的会话隔离和生命周期设计。
- 新合同盲测、端到端 Agent + 规则模块联调，以及真实 DeepSeek 否定/例外案例评估仍需后续完成。
