# 第 5 部分：检索与证据核验方案（v1.0）

项目：基于 RAG 与规则核验的商业合同审查 Agent：条款识别与证据可追溯性研究
版本：v1.0（对齐 4 号《工程架构与工具接口_修订版》）　日期：2026-11-04
代码：`tools/rag_tool.py` + `rag_core/`　测试：40 项通过

> **先说清楚边界**：本模块是 RAG 里的 **R（检索）** 加一个独立的**证据核验**环节；
> 答案抽取（G）由 4 号 Agent 的 LLM 完成。所以本文只声称"检索与证据核验模块完成"，
> 不声称"完成了 RAG 审查 Agent"。

## 1 范围与交付

| 负责 | 不负责 |
| --- | --- |
| 合同文件解析（PDF/TXT/JSON）→ 冻结规范文本 | 生成 `category_answer`（4 号） |
| 分块、偏移映射、页码回溯 | 风险规则与分级（3 号） |
| 合同内检索与候选块返回 | 重试/转人工的流程决策（4 号） |
| 引用位置核验、语义支持核验、`No` 的覆盖检查 | 人工语义评价（6/7 号） |

对外只有一个类、三个方法：`RAGTool.prepare / retrieve / verify`。

## 2 处理链路

```
文件 → 解析 → 冻结文本（归一化一次）→ 字符分块（800/120）→ 合同内 BM25 索引
     → retrieve(query, top_k) → 候选块（含 start/end/page）
     → 4 号抽取答案与引用 → verify() → evidence_checks + verification_status + coverage_status
```

## 3 分块与冻结文本

| 项 | 取值 | 说明 |
| --- | --- | --- |
| **切块策略** | **按条款标题切（默认）** | `ARTICLE 12` / `Section 12.1` / `12. LIMITATION` / `第X条`；82% 的 CUAD 合同命中 ≥3 个标题（中位数 18 个），找不到标题时自动退回字符切块 |
| 单位 | 字符（Unicode 码点） | 与 4 号的 `chunk_size=800` 语义一致，偏移可直接用于切片 |
| 块长 | 800 字符 | 单条超过 800 字符时在条款内部再切；覆盖一个完整条款段 |
| 重叠 | 120 字符 | 防止条款被切在边界 |
| 边界 | 段落 > 句子 > 空格 | 尽量不切断语义单元 |
| 归一化 | `\r\n→\n`、NBSP→空格、去零宽字符、去行尾空白、压缩空行 | 只做一次，之后所有偏移都相对这份文本 |

归一化**不可关闭**：一旦上游再改文本，`context_sha256` 变化，4 号手里的偏移立即失效——这是有意的硬性约束。
页码由解析阶段记录，`retrieve` 的块与 `verify` 的引用都带 `page`。

## 4 检索：合同内 BM25

IDF、平均长度、词频全部只在**当前合同**内统计：

```text
score(q, d) = Σ_t idf(t) · f(t,d)·(k1+1) / ( f(t,d) + k1·(1 - b + b·|d|/avgdl) )
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
k1 = 1.5, b = 0.75
```

**为什么用合同内 IDF**：跨合同统计 IDL 会引入"这份合同没用这个词"的假阴性；一份合同内
"renew/notice/audit"这类词本来就稀疏，合同内统计能把这些词的分量放大，符合"审这一份合同"的任务。

分词：小写化、`\w+`、去常见法律套话停用词、轻量词干（`-ies→y`、`-es/-s`）。

## 5 Query 构造：三种来源

| 来源 | 触发 | 实际使用的 query |
| --- | --- | --- |
| `explicit` | 调用方传了 `category` | 类别词表 + 问句 |
| `template` | 未传 `category`，问句与 4 号 `CATEGORIES` 固定问句逐字一致 | 自动按模板识别类别，加词表 |
| `none` | 未传 `category`，问句被改写 | 只用原句，不猜意图 |

为什么会这样设计：4 号的 `retrieve()` 只传 `question`，而 CUAD 的类别词表（`renew / renewal /
automatically / successive…`）才是检索信号的主要来源。用固定问句做模板匹配，可以做到"不改 4 号代码也能拿到词表"，
同时保持"不猜测用户意图"的边界——问句被改写就不扩展。

## 6 消融：query 里到底什么在起作用

510 份合同、6480 个 gold span、`top_k=5`、块覆盖 ≥80% 计命中：

| query 组成 | span R@1 | span R@5 | 精确@5 |
| --- | --- | --- | --- |
| 只用问句（不扩展） | 0.112 | 0.338 | 0.441 |
| 只用类别词表 | **0.414** | **0.719** | 0.732 |
| 类别词表 + 问句（显式 `category`） | 0.394 | 0.703 | 0.725 |
| 问句被改写后走纯检索 | 0.097 | 0.307 | 0.409 |

切块策略与检索单元对照（其余配置相同，`top_k=5`）：

| 配置 | span R@1 | span R@5 | 精确@5 |
| --- | --- | --- | --- |
| 字符块（800/120），按块检索 | 0.394 | 0.703 | 0.725 |
| **条款块，按块检索（当前默认）** | **0.405** | **0.713** | **0.744** |
| 条款块 + 句子检索回父块 | 0.369 | 0.709 | 0.743 |
| `b=0.5` / `0.6` / `0.75`（条款块） | 0.401 / 0.403 / **0.405** | 0.712 / 0.714 / **0.713** | 0.743 / 0.745 / **0.744** |

结论：

- **词表贡献 +38 个百分点**，问句几乎不贡献甚至略降；
- **按条款标题切块稳定 +1～2 个百分点**（82% 合同可用），因为条款边界就是语义边界；
- **句子级检索后再回父块没有收益**（R@1 反而降 3.6 点）：短单元让 BM25 更易被单个高频词带偏，父块聚合又把它掩盖了——所以保留为可选（`search_unit=sentence`），不作为默认；
- `b` 在 0.5–0.75 之间几乎是平的，保持 0.75。（问句里的 `what/is/the` 拉低了区分度）。
这条也是后文"为什么暂时不用向量"的证据之一：当前瓶颈是词汇不匹配，不是排序模型。

## 7 为什么首版不引入 Embedding / 向量库

不是"没想到"，是三条理由：

1. **可复现与可对照**：研究要做 A（直接 LLM）/ B（RAG+LLM）/ C（完整 Agent）三组对照，
   B 组的定义是"经固定检索"，检索必须是确定的、可逐条重放的。BM25 满足；向量模型换版本、换权重都会漂。
2. **零依赖**：评测机只有 Python 标准库。引入向量库会让"跑不通"变成环境问题，而不是方法问题。
3. **收益边界清楚**：词表检索已经把四类风险条款拉到 0.83–0.99（见 §8），剩余误差主要来自
   同义改写（"inspection" vs "audit"）与跨语言，这确实是向量检索的长处——但它应该是**对照实验**，
   用来回答"加向量能提升多少"，而不是默认实现。

**代价要写进局限**：措辞与词表不一致时召回明显下降（§6 最后一行：问句被改写后 0.31）；
这份合同没有用词表里的词表述时，BM25 完全无候选。

## 8 评测：CUAD 全量

数据：官方 `CUADv1.json`，510 份合同，6480 个 gold span（偏移先用冻结文本复核，不合法的标注剔除）。
口径：top-K 块并集覆盖 gold span ≥80% 字符计命中；`精确@K` 要求 gold 原文逐字出现在候选块内。

读法：**要审的四类（适用法律、续约、退出通知、无因终止）都在 0.83 以上**，检索层足以支撑规则判断；

## 9 证据核验

### 9.1 位置核验（程序，模型不可覆盖）

`context[start:start+len(text)] == text` 才算通过；越界、空引用、切片不一致 → `verification_status=FAILED`，
并且**不调用语义核验**。避免"位置错但内容蒙对"被放过。

### 9.2 语义核验（模型）

三态 `SUPPORTED / UNSUPPORTED / INSUFFICIENT`，逐条 + 整体 `overall_support`；
模型输出必须通过 schema 校验（索引不重、不越界、理由非空、整体 SUPPORTED 必须引用至少一条且不依赖 UNSUPPORTED），否则整批作废为 `UNCERTAIN`。
未配置密钥或调用失败同样返回 `UNCERTAIN`，不会假装通过。

### 9.3 `No` 的覆盖检查（本版新增）

空 `evidence_checks` 不能证明条款不存在。对 `No`，用类别锚定词在**全文**扫描，检查每处出现是否落在已检索块内：

| 结果 | 判定 |
| --- | --- |
| 全部出现都被检索覆盖（或全文没有该主题词） | `coverage_status=SUFFICIENT`，才可能 `PASSED` |
| 存在未被检索到的出现 | `INSUFFICIENT`，返回未覆盖位置，由 4 号改写 query 补查 |

`uncovered` 里的位置可直接用于生成"建议补查第 X 段"。

## 10 失败模式与对策

| 模式 | 现象 | 对策 |
| --- | --- | --- |
| 措辞与词表不符 | 召回下降（0.70 → 0.31） | 显式传 `category`；或补词表；向量检索列为对照实验 |
| 条款跨块 | 一处约定被切两块 | 120 字符重叠；`top_k=10` 可把 R@10 提到 0.80 |
| 否定与例外 | "shall **not** renew" 被当正向 | 检索不做极性判断；由抽取与人工核验兜底 |
| 扫描件 PDF | 无法抽字 | `prepare` 返回 `FAILED`（`PDF_TEXT_EMPTY`），不静默索引空文本 |
| 加密字体 PDF | 抽出的字是乱码 | 字符占比过低 → `FAILED`（`PDF_TEXT_UNUSABLE`），提示装 `pypdf` |
| 超长合同 | 分块爆炸 | `max_chunks` 截断并记 `warnings`；实测 3.8 万字符 / 80 块，prepare 约 7ms |

## 11 与 3、4 号的分工

| 事项 | 归属 |
| --- | --- |
| `answer_start` 的基准文本 | 本模块（`prepare` 冻结） |
| `position_valid` / `support_status` / `coverage_status` | 本模块 |
| `verification_status` 与 `coverage_status` 的解释 | 3 号规则模块读取，4 号据此决定重试 |
| `review_results` 与风险等级 | 3 号 |
| 重试次数、改写 query、转人工 | 4 号 |

## 12 局限与待办

1. **语义支持率没有独立人工标注**：现在只有模型自评与桩测试，论文里不能写成准确率。
2. **未做向量检索对照**：见 §7 的理由；若要论证"RAG 的增益来自检索还是来自 LLM"，这是下一步。
3. **锚定词表是人工初稿**：`Insurance / Audit Rights` 的表述边界需要 3 号复核。
4. **端到端未联调**：4 号的 Agent 尚未用本工具跑完一份真实合同的 11 类。
5. **PDF 逐页映射**依赖 `pypdf`；无依赖时只保证单页文本可用。
6. **条款标题识别是正则**：无编号标题（长段落式合同）会退回字符切块，此时收益归零；标题写法异常（全大写、居中、无编号）可能漏切。
7. **句子级检索实测无收益**（R@1 −3.6 点），保留为可选配置，不作为默认，避免"看起来更先进但更差"。
